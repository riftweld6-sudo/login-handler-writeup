Case study 014 · Authentication bypass

One assertion to a session: the login handler that trusted email

An unauthenticated login request could reach a fallback provider branch that decoded a client-supplied assertion and trusted its email claim. When the account's device-trust check was satisfied, that was enough to mint a session; an unregistered email became a confirmed account. A sanitized, lab-confined reconstruction.

Summary

What happened, and what we did

An unauthenticated request to the login endpoint could reach a fallback provider branch that decoded a client-supplied identity assertion and used its email claim to find or create an account. The branch did not verify the assertion's signature, issuer, audience, or lifetime. The only remaining gate was device trust: when the presented device pair was already trusted for the account, the service minted a session; otherwise it returned a mailbox challenge. An unregistered email created a new confirmed account. The root cause was not a clever payload. It was a trust decision made in the wrong order.

  • Reachable by anyone: an unauthenticated POST /v1/login with a provider value outside the validated set.
  • Three outcomes: an existing-account session when device trust was satisfied, an account factory for unregistered emails, and an adoption persistence layer after a later password reset.
  • Scope: all testing was lab-confined, with self-owned accounts and synthetic data. No third-party system was touched.
  • Fix: verify the assertion before any account lookup, map by (iss, sub), and remove the permissive fallback branch.

Scope

What this publication can and cannot establish

Can establish

  • The fallback branch decoded and trusted the assertion without signature, issuer, audience, or time validation.
  • The device-trust gate, its preconditions, and the difference between a trusted and an unknown device.
  • The account factory and the adoption persistence layer, reproduced with self-owned accounts.
  • The fix: verification before lookup, a closed provider allowlist, and device policy applied after identity verification.

Cannot establish

  • Universal zero-click takeover. The device-trust check was real and blocked unknown devices.
  • MFA bypass. Accounts with an additional factor took a different challenge path.
  • Production exploitation. No production system, customer account, or third-party data was used.
  • Original discovery. This is a sanitized case study, not a claim of first report or victim impact.

Root cause

A fallback branch that trusted the request body

The login service had a branch per provider. Each known provider validated its own assertion, then mapped the result to a local account. That was the intended design.

The default branch was different. When the provider value did not match a validated provider, the handler fell through to an arm that treated the assertion as if an earlier step had already verified it. It decoded the token, read the claims, and used email to find or create an account.

// fallback branch, simplified
const claims = decode(assertion);        // decode, not verify
const user = await users.findByEmail(claims.email);

if (await deviceIsTrusted(user, deviceFingerprint)) {
  return issueSession(user);
}

Three things compound. First, decode parses a token; it does not establish who issued it. Second, email is a mutable profile field, not a stable identity key. Third, the handler asked whether the device was trusted before it had established that the assertion was trustworthy.

The device check was not the bug

Device trust can answer “have I seen this device before?” It cannot answer “did this identity provider vouch for this person?” The bug was that, on this path, it was the only check left.

Consequences

Three outcomes, one root cause

Existing account

Session, if the device is trusted

A trusted device pair plus a forged assertion returned 200 challengeType 0 and an authorization code. The resulting session read the profile. From an unknown device, the same request returned 202 and no session.

Unregistered email

An account factory

The same branch auto-provisioned an account for an unregistered email and marked it confirmed. At the measured sample, the flow allowed one request per account and showed no rate limit.

Adoption

Trust that survived a reset

An attacker could squat an address, wait for the owner to register and reset, and keep device trust across the reset. A post-reset forged login from the squatting device reached the adopted account silently.

These are not three separate vulnerabilities. They are three ways the same missing verification expresses itself: a session for an account that already exists, a new account that should never exist, and a persistence layer that survives the owner's recovery attempt.

The chain

From unauthenticated POST to session

Phase A: an existing account with a trusted device

POST /v1/login HTTP/1.1
Host: api.example.test
Content-Type: application/json

{
  "provider": "unexpected-provider",
  "assertion": "<client-supplied identity assertion>",
  "email": "victim@example.test",
  "deviceFingerprint": "<trusted-device-fingerprint>",
  "deviceRequestId": "<trusted-device-request-id>"
}
HTTP/1.1 200 OK
Content-Type: application/json

{
  "challengeType": 0,
  "authorizationCode": "<opaque-code>",
  "user": {
    "id": "<victim-user-id>",
    "email": "victim@example.test"
  }
}

The authorization code could be exchanged for a session, and the session could read the profile. The same request from an unknown device returned 202 with a mailbox challenge and no session. Missing device fields returned 400.

Phase B: an unregistered email

Change the claim to an address that does not exist yet. The branch creates a new identity, marks it confirmed, and makes the forging device the account's first trusted device. The attacker now has a normal-looking consumer account without proving control of the mailbox.

Phase C: adoption after a later reset

If the real owner later registers and resets the password, the reset does not necessarily evict the squatter's device trust. The post-reset forged login from the squatting device can still return 200, while the owner's own new device is challenged. That is the persistence layer, and it is why “the account was empty” is not a complete mitigation.

Forged assertion, unknown device202, mailbox challenge, no session

Impact

High, with a precondition that matters

For an existing account, the impact is a full session: profile reads and user-level actions as the victim. The precondition is real. The attacker needs a trusted device pair or the ability to complete the mailbox challenge. That is why this is High rather than Critical, and why “any unauthenticated request can take over any account” would be the wrong claim.

For an unregistered email, the impact is an account factory: attacker-created identities that look confirmed, can consume trial or promotional entitlements, and can be used as the anchor for an adoption attempt. The measured sample showed no rate limit on the direct path.

The forged identity was also accepted by a separate legacy storefront, which exposed order history and profile data. That downstream trust is the broader lesson: the login endpoint was not the only relying party. Every service that accepts the session must either validate the assertion or trust only the session minted after validation.

The fix

Verify first, then decide

The fix is not a better regex or a longer blocklist. It is a different order of operations, plus a smaller attack surface:

  1. Verify before decode. Treat every client-supplied assertion as untrusted input. Verify the signature with the issuer's current JWKS, enforce an algorithm allowlist, and reject none.
  2. Pin the context. Check iss against the expected issuer and aud against your client ID. If the token can carry multiple audiences, check the authorized party as the specification requires.
  3. Enforce time. Reject expired tokens, tokens that are not yet valid, and tokens issued outside a small clock skew.
  4. Map by (iss, sub). Use the stable subject identifier. Treat email as profile data, not as a primary key.
  5. Delete the fallback. Replace the default provider arm with an explicit allowlist. Unknown providers should fail closed, not fall into a permissive branch.
  6. Keep device trust in its lane. Apply device policy after identity verification. A trusted device can reduce friction; it cannot substitute for proof of identity.
// Pseudocode. Use a maintained library and your provider's JWKS.
const { payload } = await verifyAssertion(assertion, {
  algorithms: ["RS256"],
  issuer: TRUSTED_ISSUER,
  audience: CLIENT_ID,
  clockTolerance: 60
});

const user = await users.findByProviderSubject(payload.iss, payload.sub);

// Device policy is a second decision, not a replacement for the first.
if (!(await deviceIsTrusted(user, deviceFingerprint))) {
  return challenge(user);
}
return issueSession(user);

Centralize the verification function and make every login path call it. Then add the negative matrix to CI: self-signed, alg: none, wrong issuer, wrong audience, expired, future-dated, and wrong-subject assertions. Test the branch you think is dead.

Lab method

How the reconstruction was verified

The work ran in a controlled staging environment with self-owned accounts and synthetic claims. The harness minted assertions with controlled properties and presented them to the login endpoint. Each test changed one property at a time: signature, algorithm, issuer, audience, time, device state, or email registration state.

Assertion variantCorrect resultObserved result
Signed with a key the server never checkedRejectAccepted

Correction we published forward

An early run used a malformed request body and returned 500, which looked like a patch. The harness-exact shape reproduced the 200. The false negative is kept in the record. Separately, the device key was the visitor pair resolved from the request identifier, not the claimed string; that correction matters for anyone trying to reproduce the precondition.

Everything in this write-up is synthetic: the domains, the accounts, the assertion values, and the session identifiers. The repository contains the sanitized write-up and no live credentials, tokens, or customer data.

Disclosure

Responsible publication

This issue was responsibly disclosed to the affected program. The program reviewed the finding, fixed it, and permitted this sanitized write-up for educational purposes. All company names, domains, IP addresses, endpoints, user identifiers, and customer data have been removed or replaced with synthetic values such as api.example.test, victim@example.test, and CVE-202X-XXXXX.

The proof of concept is conceptual. It shows the trust boundary and the failing order of operations, not an actionable, unremediated exploit payload. CVE-202X-XXXXX is a placeholder; no CVE was assigned to this sanitized case study.
